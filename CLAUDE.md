# Глобальные правила работы

## Язык и общение
- Все объяснения, комментарии в коде и ответы — на русском языке
- Если задача неясна — уточнять, не угадывать
- Отвечать структурно и по делу, без вводных фраз
- Действовать автономно по умолчанию: изучить, принять решение, реализовать, проверить, доложить — без лишних циклов согласования
- Уточнять только когда неоднозначность блокирует безопасное решение, или действие деструктивно и необратимо настолько, что пользователь должен выбрать явно
- Не галлюцинировать. Проверять неочевидные утверждения через код, скрипты, вывод в терминале или содержимое файлов репозитория

## Работа с файлами
- Изменения в существующем коде — выполнять без запроса
- Создание новых файлов — спрашивать перед созданием
- Удаление файлов или пакетов — спрашивать перед удалением: явно написать что именно удаляется и почему; любое деструктивное, необратимое или затрагивающее данные пользователей действие требует явного подтверждения
- Не выводить в ответах токены, API-ключи, значения из .env, данные пользователей и любые другие секреты — даже при диагностике
- Не добавлять реальные секреты в комментарии, логи, документацию или любые файлы, которые могут попасть в репозиторий

## Работа с памятью сессии
- При старте новой сессии — проверять наличие progress.md и читать его первым
- Если progress.md нет — начинать с чтения CLAUDE.md проекта
- **Архивация progress.md:** при чтении progress.md найти записи старше 3 дней от текущей даты, переместить их в progress_archive.md (дополнить), перезаписать progress.md только с актуальной информацией (последние 3 дня). progress_archive.md не читать автоматически, хранить как архив.
- **Формат progress.md и progress_archive.md:** компактный вид — одна строка на пункт, максимум: название функций и файлы, суть решения, критические баги. Без размеров БД, команд проверки, технических логов. Файлы указывать компактно через запятую (папка,файл).

## Актуализация документации
- Конкретные изменения (какие файлы, что сделано, почему) — писать только в progress.md
- В CLAUDE.md обновлять только раздел «Текущее состояние»: отражать актуальный статус функций, не дублировать детали из progress.md
- Если изменение затронуло стек или структуру проекта — дополнительно обновить соответствующий раздел (Стек / Структура проекта)
- Остальные разделы не трогать без явной команды

## Работа с задачами

### Классификация задач
Перед выполнением определить тип задачи и соразмерить процесс задаче:

- **Прямая** — косметика, текст, отступы, комментарии, очевидные локальные правки, не меняющие поведение в рантайме. Изучить затронутый файл и ближайший контекст, внести минимальное связное изменение, выполнить узкую валидацию если это быстро и уместно.
- **Диагностика** — отладка, когда первопричина или путь ошибки ещё неясны. По возможности воспроизвести или отследить наблюдаемый сбой, определить владеющий слой, остановиться и переосмыслить если две попытки не продвигают основной сигнал.

### Общие правила
- Выполнять задачи последовательно, сообщать об этапах кратко
- Если в процессе обнаружено несоответствие в коде — сообщить, не исправлять молча
- Тяжёлые проверки (импорты всего проекта, полный анализ) — только по явной команде

### Минимальное достаточное изменение
- Стремиться к наименьшему связному изменению, которое полностью решает реальную проблему в слое-владельце
- Предпочитать плоские простые реализации — без лишних слоёв, папок, паттернов и абстракций
- Не добавлять абстракции, вспомогательные функции, обёртки, папки или генераторы если они не устраняют реальную текущую сложность
- Если решение очевидно и малорискованно — выполнить его
- Если сделано безопасное предположение — выполнить и указать это предположение в итоговом отчёте

## Правила работы с кодом

### Общие
- Читать только файлы, относящиеся к задаче — не сканировать весь проект
- Опираться на актуальный код, вывод в терминале и реальное состояние сервиса — а не на устаревшую документацию; при расхождении — доверять коду
- Не запускать тяжёлые импорт-проверки без явной команды
- После изменений проверять синтаксис только изменённых файлов: `python -m py_compile файл.py`
- PostgreSQL не использовать — только SQLite
- После каждого этапа писать краткий итог что было сделано

### Запуск после задачи
Если в запросе есть фразы «для тестирования», «чтобы тестировать», «для дальнейшего тестирования» — в самом конце после всех изменений выполнить:

```bash
# Smoke-тест перед запуском
venv/bin/python -c "from bot.main import *; from admin_bot.main import *; print('OK')"

# Перезапуск
systemctl restart transformation-bot

# Проверка успешного старта
sleep 5 && systemctl is-active transformation-bot && tail -20 run.log
```

Сообщить результат: запущены успешно или вывести ошибку из лога.

## О проекте
AI-бот для обучения навыкам отстаивания личных границ через диалоги и интерактивные тренировки. Помогает людям распознавать границы, понимать свои чувства и уверенно коммуницировать в сложных ситуациях.

## Стек
- Python — только `venv/bin/python` (НЕ системный python)
- Telegram-боты — aiogram 3.x + FSM (два бота: пользовательский + админский)
- LLM — OpenRouter API: основная модель openai/gpt-4o-mini, fallback openai/gpt-oss-120b:free (openai-совместимый клиент)
- Векторная БД — ChromaDB + sentence-transformers (paraphrase-multilingual-MiniLM-L12-v2)
- БД — SQLite (sqlite3 напрямую). Таблицы: messages, user_profiles, summaries_history
- Планировщик — APScheduler
- Текст — langchain-text-splitters, pdfplumber, python-docx

## Переменные окружения (.env)
```
TELEGRAM_TOKEN       — токен пользовательского бота
ADMIN_BOT_TOKEN      — токен админ-бота
OPENROUTER_API_KEY   — ключ OpenRouter
ADMIN_TELEGRAM_IDS   — список admin ID через запятую
DB_PATH              — путь к SQLite файлу
VOSK_MODEL_PATH      — путь к папке модели Vosk (по умолчанию: vosk/vosk-model-small-ru-0.22)
```

## Запуск и управление
```bash
# Перезапуск после изменений
systemctl restart transformation-bot

# Статус и проверка запуска
systemctl status transformation-bot

# Логи в реальном времени
tail -f /opt/transformation-bot/run.log
```

Параметры сервиса:
- Точка входа: `venv/bin/python run.py`
- `run.py` запускает оба бота через `asyncio.gather()`
- Restart=on-failure, пауза 5 сек
- Лимит: 700MB RAM + 500MB swap

## Управление памятью сессии
Лимиты сервера: 961MB RAM, лимит сервиса 700MB RAM + 500MB swap. OOM-падений не было — следить за этим.

Мониторинг памяти перед тяжёлыми задачами (затрагивают ChromaDB или sentence-transformers):
```bash
free -h && systemctl status transformation-bot --no-pager | grep Memory
```

Обновлять файл `/opt/transformation-bot/progress.md` автоматически в двух случаях:
1. После тяжёлой многоэтапной задачи
2. Каждые ~20 сообщений в текущей сессии

Формат записи:
```
## [дата]
Задача: [что делалось]
Сделано: [список изменённых файлов и что изменено]
Что изменено и почему: [краткое обоснование каждого изменения]
```

## Текущее состояние (обновлять при изменениях)

* Режим работы: текстовый и голосовой ввод
* Голосовой модуль: **ВКЛЮЧЁН** (2026-04-30)
  - Vosk 0.3.45 + ffmpeg для OGG→WAV конвертации
  - Доступен в режимах `in_situation` (описание ситуации) и `in_trainer_answer` (варианты ответов)
  - Синглтон-модель Vosk загружается один раз при первом запросе и кэшируется в памяти
  - Качество транскрипции: хорошее, без пунктуации (норма для Vosk small)
  - Время обработки голоса: ~2-3s на транскрипцию + стриминг LLM-ответа
* Архитектура режима «Ситуация»: **двухшаговый pipeline** (2026-05-01)
  - **ШАГ 1 (скрытый)**: Диагностика ситуации — анализ психологического механизма, внутреннего перевода, симптомов, скрытых причин. Вызов `_diagnose_situation()` → JSON результат
  - **ШАГ 2 (основной)**: Генерация полного ответа. System_prompt расширяется блоком диагностики (если шаг 1 успешен) + блоком сводки пользователя (если есть история). Вызов `generate()` → reply (финальный ответ)
  - **ШАГ 3 (удалён)**: Пост-проверка была убрана — добавляла 2–4 сек времени ответа при маргинальном приросте качества. Основная модель (openai/gpt-oss-120b) достаточно качественна.
  - Всего 2 вызова LLM на каждую ситуацию. Шаг 1 обёрнут в try/except, ошибка не прерывает pipeline (fallback: диагностика = None)
  - Время ответа: ~5–10s вместо прежних ~7–14s (ускорение −30%)
* Сводки пользователей: **пересчитываются по всей истории** (2026-04-30)
  - Ежедневный job (03:00) теперь вызывает `create_summary(user_id, hours=None)` — полный пересчет по всей истории
  - Ручное обновление в админ-боте ("🔄 Обновить сводки") также использует `hours=None`
  - Сводка загружается в начале `_handle_text()` и добавляется в system_prompt перед основным вызовом
  - Полная история обеспечивает устойчивый и правильный контекст для диагностики и анализа
* Скрытие кнопок: реализовано в пользовательском боте — callback-хэндлеры вызывают `callback.message.edit_reply_markup(None)`, message-хэндлеры используют `_clear_last_keyboard`
* Промт оценки тренажёра: trainer_eval_prompt.yaml активен. Оценка отправляется после основного фидбека. Редактируется через кнопку "🏋️ Тренажёр ответов" (переименована из "✏️ Промт оценки тренажёр", старая кнопка "🏋️ Тренажёр" удалена)
* venv: пересобран без CUDA/nvidia библиотек (CPU-only PyTorch). Добавлены: vosk==0.3.45
* Base знаний: ОТКЛЮЧЕНА в админ-боте (knowledge.router не зарегистрирован в admin_bot/main.py). knowledge/indexer.py остаётся в коде но не импортируется
* ChromaDB: ленивая загрузка из функции `_get_collection()` в ai/rag.py
* LLM-модель: **openai/gpt-4o-mini** (основная) + fallback **openai/gpt-oss-120b:free** (2026-05-02)
  - При ошибке основной модели → автоматическое переключение на fallback без прерывания пользователя
  - Параметры: temperature=0.6, top_p=0.85 (применяются к обеим моделям)
  - Логирование скорости: каждый вызов LLM пишет [TIMING] с временем и count токенов
  - Замеры: диагностика ~3s, основной ответ ~5-12s, тренажёр ~3s
* Запуск: optimized. systemctl restart занимает ~28s (systemd timeout). systemctl start занимает ~1s до готовности
* Оформление: заголовки разделов в ответах переведены на жирный шрифт вместо цитат
* Админ-бот: добавлена кнопка "💰 Баланс OpenRouter" для проверки остатка средств (api: /v1/credits)
* **Система Changelog: готова к production** (2026-05-02)
  - **Pipeline**: progress.md → watcher (watchdog) → LLM (extractor+transformer) → pending.json → админ-бот → GitHub API → data/changelog.json → GitHub Pages

## Ведение Changelog entries

При обновлении `progress.md` — одновременно добавлять записи в `changelog/data/entries.json`.

### Формат entries.json
```json
[
  {
    "date": "2026-05-03",
    "group": "Интерфейс",
    "changes": ["Обновлено отображение — теперь понятнее", "..."],
    "published": false
  }
]
```

### Правила написания изменений
- Формат каждого изменения: `[Действие][Что] — [Как помогает]`
  - Пример: "Обновлён формат сообщений — важные разделы выделены для лучшей читаемости"
- Максимум 3 изменения на одну запись (date+group). Если больше — создать вторую запись с той же датой и группой
- Без технических терминов: не "промт/FSM/LLM/хэндлер/пайплайн", а "инструкция/режим/система анализа/функция/система"
- Без упоминания файлов и папок
- Без номеров шагов ("Удалён шаг 3")
- Без технических названий моделей (GPT-4o-mini, OpenRouter)
- Без смайликов в тексте изменений

### Группы (выбирать одну на запись)
- **Интерфейс** — текст, кнопки, структура сообщений
- **Логика** — как бот анализирует и отвечает
- **Баги** — исправления ошибок
- **Архитектура** — новые инструменты, поддержка функций
- **Оптимизация** — скорость, качество, эффективность
- **Админ. панель** — функции админского бота

### Когда добавлять
- После каждого обновления progress.md
- Только для изменений, видимых пользователю или меняющих поведение системы
- Инфраструктурные/технические изменения (логирование, рефакторинг без изменения поведения) — не добавлять
